# What Parity supports

Parity's `.par` and `.lib.par` files each have one current format (`version: 4`); obsolete library formats are rejected
rather than migrated. Modes and clipboard envelopes each accept only their current format (`version: 1`). Format
identifiers do not introduce parallel implementations. Library aliases are resolved during discovery, including
providers, nested sample values and icons.

What works today, what needs an adapter, and what Parity asks of every project. Keep this current: when an adapter,
connector or lens lands, update its row here. The visual version is the
[Parity support matrix](https://claude.ai/artifact/KdDtEs9y2Thiz5u9LW8Wgu); republish it when this changes.

| Status | Meaning                        |
| ------ | ------------------------------ |
| ✅     | Works, and tested              |
| ◐      | Works, with limits             |
| ❔     | Should work, untested          |
| 🔜     | Planned, in a written proposal |
| ⏳     | Later, not scheduled           |
| ❌     | Not supported                  |

Everything here was read from the code on 2026-10-28. Only one stack is tested end to end: the example project
(`examples/shadcn-vite`), which is React 19, Vite 8, Tailwind CSS v4, shadcn, TypeScript 6 and TanStack Router with
file-based routes (PAR-1072). The validation projects at the end of this page are the plan for testing more. Four of
them exist in `fixtures/` (`vite7-js`, `react-aria`, `mantine` and `too-old`), so far checked by their detection
snapshot only.

## Four kinds of requirement

| Kind         | What it means                                                                                                 | Today                                                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| **Fixed**    | Parity's design depends on it. No adapter will remove it.                                                     | A Node package, a web UI drawn to the DOM, ES modules from a dev server, styles as stylesheets, tokens as CSS custom properties, `.par` files  |
| **Expected** | Assumed for speed. Nothing else is built for now. A project without it gets less, and an adapter can lift it. | TypeScript, React 18 or 19, Vite 7 or later, Tailwind CSS v4, named exports                                                                    |
| **Standard** | Read from an open format, so any tool that writes it works.                                                   | CSS custom properties, WCAG 2.2 through axe-core; planned: OpenAPI, JSON Schema, SQL, DTCG; later: JUnit XML, LCOV, OpenTelemetry, OpenFeature |
| **Adapter**  | One piece of code or data per tool. The first ones are built, others follow by demand.                        | React, Vite, Tailwind v4, `.lib.par` libraries, Lucide, Storybook                                                                              |

### Fixed

1. **A Node package.** A `package.json` is how Parity finds the framework, the libraries and the package manager.
2. **A web UI drawn to the DOM.** Frames are real DOM in shadow roots. Native and terminal UIs need their own frames,
   which the web-and-backend plan puts after the web.
3. **ES modules from a dev server.** Whatever the build tool, it has to serve the canvas an ES module it can import.
4. **Styles as stylesheets.** Frames adopt the project's CSS into each shadow root, and so do the stylesheets its code
   adds to the page, whichever builder or library adds them: CSS modules, and CSS-in-JS that writes into the page's
   head. Styles CSS-in-JS writes elsewhere reach frames only when a decorator sends them there, as the Emotion and
   Griffel libraries' decorators do. What Emotion writes there is drawn as the project's stylesheets are.
5. **Tokens as CSS custom properties.** Modes switch themes and breakpoints on each frame, and token edits are CSS
   variables. Tokens can be written in any format, as long as they compile to custom properties.
6. **Designs in `.par` files** in the repo, as JSON.

### Expected

| Expectation         | Why it pays                                                                                               | Without it                                                                                 |
| ------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| TypeScript          | One engine, the type checker, gives props today and component discovery, API clients and code links next. | Designs render, but props aren't inferred.                                                 |
| React 18 or 19      | One renderer adapter to build and test. React 17 and earlier are dropped.                                 | It opens as usual, but React 17 and earlier aren't tested and may not render.              |
| Vite                | One builder adapter; it loads the project's own config.                                                   | The project doesn't open (no builder adapter).                                             |
| Tailwind CSS v4     | The theme is read and written as `@theme`; spacing and type scales come with it.                          | Plain CSS variables still give tokens; the spacing scale and `@theme` editing are missing. |
| Exported components | Parity places what code can import. Named and default exports both work.                                  | A component used only inside its own file isn't listed.                                    |

## By kind of tool

Every tool Parity opens projects with is an extension, which describes what it provides in its package.json and answers
through its host. The project service lists Parity's own extensions in `apps/desktop/src/utility/extensions.ts`;
supporting a new tool means writing its extension and adding it there. Each extension brings its tool's logo, which its
status bar item shows.

When a project opens, every adapter's `detect` is asked, all through the same context (the root, its package.json and
its files), whether the project uses its tool; it says what it found and its config file, and a builder asks its build
tool for its version. The first renderer and builder that find their tool are used, and every other adapter that finds
its own. Files an adapter `watches`, such as Vite's or Storybook's config, detect the project again when they come or
go.

### Tokens

| Format                                     | Status | Notes                                                                                                                                                                                                                                                   |
| ------------------------------------------ | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CSS custom properties on `:root`           | ✅     | Read and written. A token an agent adds with `SetTokens` goes into `:root`, a theme's value into that theme's block.                                                                                                                                    |
| Tailwind `@theme`                          | ✅     | Read and written, including `@theme inline` and `@theme static`. | Tailwind keywords (`rounded-full`)         | ◐      | `radius-full` in the radius field is `rounded-full`, unless the project declares `--radius-full`. `GetTokens` lists it as `source: "keyword"`; the inspector's picker doesn't offer it yet. | Tailwind easings and transition defaults   | ✅     | A transition's `ease-out` and an unset time or easing use the project's `--ease-out` and `--default-transition-*`, and Tailwind's own values where the project doesn't write them. | Spring easings                             | ◐      | CSS has no spring, so a transition on a spring is drawn with a `linear()` curve through the spring's path, sampled up to 60 times over its settle time, which is the transition's duration. | Themes as one class (`.dark`)              | ✅     | Also on the root (`html.dark`, `:root.dark`). `.light` is the default.                                                                                                                                                                                  |
| Themes as attributes (`[data-theme]`)      | ✅     | Read, written in place and shown: `[data-theme="dark"]` is the `dark` theme, and a frame in the Dark mode gets `data-theme="dark"` with its `dark` class. | `prefers-color-scheme` blocks              | ✅     | Read, written in place and shown: `(prefers-color-scheme: dark)` around the root is `dark`, below a `.dark` or `[data-theme]` value, and `light` the default. | Selectors that only scope a theme          | ❌     | `.dark .card`, `.dark.contrast` and `:where(:root, :host)` name no theme.                                                                                                                                                                               |
| Layer order tokens (`--z-*`)               | ✅     | A custom property named for z-index (`z-`, `zindex-` or `layer-`) that comes to a whole number is offered in Layer order. | Shadow and blur tokens                     | ◐      | Effects offers shadow tokens by kind (box, inset and drop) and blur tokens. A color set over a shadow token isn't drawn in frames yet, since its variable can't be recolored.                                                                           |
| Breakpoints (`--breakpoint-*`, `.lib.par`) | ✅     | Plus device presets.                                                                                                                                                                                                                                    |
| DTCG token files and resolvers             | ✅     | Read from a `.lib.par`'s `tokens`, filed by the category `$extensions.parity` gives, each theme as a mode. A malformed token is left out, and the project's notes say why. Buildkit's styles ship one, which `parity lib` copies in.                    |
| JavaScript themes (MUI, Chakra, Fluent)    | ✅     | Read by `parity lib` into the registry's DTCG.                                                                                                                                                                                                          |

**The project's preview file, `.parity/preview.tsx`,** has Storybook's preview exports and runs without Storybook, on
every builder: its decorators wrap every frame inside the libraries', with Storybook's context, and its loaders run as a
frame mounts. **Without it, Storybook's own `.storybook/preview.*`** wraps every frame, composed with the project's
`@storybook/react` (or the React framework that re-exports it) through Storybook's portable stories API, so its
decorators, loaders and parameters apply as in Storybook (PAR-98). Global types give only their defaults, not mode
variables (PAR-105), and parameters are the preview's, not a design's (PAR-106). `definePreview` previews apply with
their `addons` (PAR-97); other add-ons' annotations (PAR-112) aren't applied yet.

**Story files are read as story designs (read-only viewer).** `EntitiesAdapter` in `@parity-app/core` translates a
tool's own files to Parity's entities, and back: it reads what Parity doesn't, and gives back what it does. Each tool is
an extension: Vite, React, Tailwind CSS, TanStack Router, React Router and Storybook, whose entities provider reads CSF
with the TypeScript compiler: each story file is a design of the story kind, its stories its states, a row each on its
board. A story whose meta names a component and has no `render` of its own draws that component with the story's args as
its props. A story that renders itself draws its `render` function, loaded from its file, with its args as props.
Decorators and the `render` function's `context` aren't applied yet. Edits to a story's args are written back to its
file, as the args that differ from its meta's; nothing else of a story file's design is. Layers lists the files in
folders for each part of their titles, with Storybook's kinds of icon for a group, a file and a story. Each story draws
a preview for each mode it shows, as wide as the story, in the mode's whole window, and the picked story's args show as
Props in the Design panel. Sizes dragged on a story to test it, its modes and their scales are kept in the project's
file, never in the story's.

**Routes are read (PAR-1073), and each page is drawn as a screen (PAR-1076).** A router extension's provider gives the
routes (PAR-1095), as `Route` in `@parity-app/extension` describes them, in Parity's terms rather than the router's
(PAR-1132): each route's id, kind (root, layout, group or page), URL as segments (fixed, param, catch-all or optional
catch-all), parent, file, whether it's an index, the component it draws, and whether it loads data or guards the page.
Parallel routes' slots and intercepting routes have room in the shape but aren't drawn yet. The TanStack Router
extension (`packages/extension-tanstack-router`) reads TanStack Router's file-based routes from the route tree its
tooling generates (`src/routeTree.gen.ts`, or where `tsr.config.json` puts it) and each route's file. Routes written in
code without the generated tree aren't read. The React Router extension (`packages/extension-react-router`, PAR-1145)
reads framework mode's `app/routes.ts` (`route`, `index`, `layout` and `prefix`), the file-based routes `flatRoutes()`
makes, and library mode's route objects or `<Route>` elements, without running the app; routes it can only know by
running the app are named as not supported yet in its status item's tooltip. See
[editor.md](editor.md#react-router-as-an-extension-par-1145). The Next.js extension (`packages/extension-nextjs`,
PAR-1162) reads the App Router's `app/` and the Pages Router's `pages/`, at the root or in `src/`, both in one project:
folders and files as segments, `[id]`, `[...slug]` and `[[...slug]]`, nested layouts, `(group)` folders, `index`, and
`_app` as the Pages Router's root, inside the App Router's root layout when there are both. `loading`, `error` and
`not-found` files, and `404`, `500` and `_error`, are named as the route's state files. Parallel `@slot` routes and
intercepting `(.)`, `(..)` and `(...)` routes are read with their slot and the route they intercept, and left off the
canvas. Private `_folders`, route handlers, `_document` and `api/` aren't routes. Its pages draw once a builder serves
the app. Each page is a screen, laid out in the router's tree, whose frames load the app itself at the page's URL (see
editor.md), with each path param's value set in Props.

**Pages run the page runtime (PAR-1260),** which Vite, the webpack-compatible builders and Next serve first in the app's
page, so a page changes mode without loading again and says how tall it is and where it went. Each project's pages load
under a `.localhost` name of its own, so they run in a process of their own; Vite, webpack-compatible builders and Next
all serve those names. What the runtime knows of the app comes from its extensions' page modules:

| Router or renderer                                   | Page module                                                                                                                                                              | Status |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------ |
| TanStack Router                                      | Moves the app with its own router, read from `window.__TSR_ROUTER__`                                                                                                     | ✅     |
| React Router, framework mode                         | Moves the app with its own router, read from `window.__reactRouterDataRouter`, which `HydratedRouter` sets in v7 and v8                                                  | ✅     |
| React Router, data library mode                      | Moves the app with the router its `createBrowserRouter` or `createHashRouter` made, which Vite and the webpack-compatible builders serve through Parity's `react-router` | ✅     |
| React Router, declarative or from `react-router-dom` | None: `<BrowserRouter>` makes no router object, and only `react-router` is wrapped, so the page is moved only by loading it at the route                                 | ◐      |
| Next.js, App and Pages Routers                       | Moves the app with its own router, read from `window.next.router`                                                                                                        | ✅     |
| React, Next.js's included                            | Says when the app has hydrated, from React's first commit to its root                                                                                                    | ✅     |
| Any other renderer                                   | None: the page counts as hydrated once loaded and quiet for 150 ms                                                                                                       | ◐      |

The routers' globals aren't public API, so each page module checks what it finds, and a page whose global is missing or
changed is moved only by loading it. Each says a move is done once the new page is in the DOM: TanStack Router once it
has resolved, React Router at the page's first change after the router settles (or 100 ms without one when the move
matches the same routes), the App Router when it writes the address of the move as it commits, and the Pages Router when
its `push` resolves. React Router says not-found when no route matched or a loader threw a 404; the App Router from the
marker its development build puts in `<head>`; the Pages Router from its `/404` and `/_error` pages.

Hydration and navigation in the fixtures' real apps are checked only by the end-to-end suite, which doesn't cover them
yet.

A backend in any language works with the lenses that read standards: OpenAPI, SQL and OpenTelemetry don't care what
wrote them.

## Decided

You agreed to the four tiers as recommended on 2026-10-28. The choices inside them:

- **TypeScript expected, not required.** JavaScript projects keep rendering, and no JavaScript-only fallbacks get built.
- **React and Vite only, until a second adapter is asked for.** Next.js is the likely second builder; Vue and Svelte the
  likely next renderers.

## Version cutoff

**Anything released more than two years ago is dropped.** Each major version counts from its own first stable release
(x.0). Dropped means not tested: no fixes and no validation project. It doesn't mean blocked. In your words: "By drop
support, I didn't mean prevent others from using those versions, just that we don't actively test and support them." A
project on a dropped version opens and works as far as it can. Parity reads the installed version of each tool an
adapter finds (React, Vite, Tailwind CSS, TanStack Router, React Router and Storybook) and notes an untested one
quietly, in the status bar's tooltips and the agent API. Each adapter gives its tool's packages and the date of each
major (`Adapter.versions`), so a new adapter brings its own cutoff; add a major there when it comes out. A tool whose
extension exists, React, Storybook, TanStack Router, React Router and Next.js so far, takes its versions from the
extension's peer dependencies instead: inside the range is supported, above it newer and below it dropped, and the range
is widened or narrowed in the extension's `package.json` as this policy says. A version read from another of its peers
is checked against that peer's own range, as Next.js against `next`'s when the webpack builder runs a Next.js app.

- **A tool's newest major is never dropped,** however old it is, as you confirmed. Otherwise React 19 would drop in
  December 2026 with nothing to replace it, and Fluent UI v9, from 2022, would already be gone.
- **It covers every tool Parity runs, renders or reads,** including ones it doesn't support yet: UI frameworks, build
  tools, styling, component and icon libraries, Storybook, test runners, routers, ORMs and API frameworks. Package
  managers follow what the detector below supports.
- **A 0.x line counts as one version, dated by its last 0.x release,** since every 0.x release can break. lucide-react's
  0.x line ended in March 2026, so it stays supported until March 2028.
- **A version with less than six months left gets no new work.** It's kept working as it is, but nothing is built or
  tested only for it. Vite 6, React Router 7, Prisma 6, Astro 5, Vitest 3 and MUI 7 are in that window now.
- **Each tool is tested at its newest major, and at its oldest major with more than six months left,** in the validation
  projects below. Today that's React 19 and 18, Vite 8 and 7, Tailwind v4, Storybook 10 and 9, and Next.js 16.

### What runs against each project

The same checks run on every project, from fastest to slowest:

1. **Detection snapshot.** Parity's detection runs on its own, with no window, and its result is compared with the
   project's committed `expected.json`: build tool and version, config file, styles, tokens, themes, breakpoints,
   components, libraries, icons, package manager, Storybook, and the lenses' sources. It runs in `vp run test`, from
   `packages/fixtures/src/detection.test.ts`. Tokens come from the stylesheets' sources there, where the app reads the
   CSS Vite compiles from them.
2. **Render sweep.** Every component with its default props, and every design in every state and mode, is drawn as a
   page of its own on the project's dev server, isolated as a browser tab is. Any render error fails it, and screenshots
   are compared with the project's baseline. Each canvas frame's layout is then checked against its page's.
3. **Editor flows,** driven through the app as `scripts/drive.ts` does now:
   - insert a component, edit a prop, change a token, switch theme and breakpoint;
   - copy and paste, drag to reorder, undo and redo;
   - save, reopen, and check the `.par` round trip;
   - paste an image, export PNG and SVG, run the accessibility check, try the design in Interact mode;
   - open a component in Storybook, and add a library in a copy of the project.
4. **Lens checks,** for projects with a backend: tables, operations and routes match the expected models, and mock data
   is served.
5. **Unsupported and untested projects** (`next`, `too-old`): `next` gets the expected "not supported yet" message, and
   `too-old` opens and works as far as it can, with a quiet note that its versions are untested. Neither crashes, and
   nothing is written to either project.

### How they're kept

- **Generated, then committed.** A script creates each project with the tools' own scaffolders at pinned versions, such
  as `create-vite`, `create-next-app`, `shadcn` and the Buildkit scaffolder. The projects are committed with their
  lockfiles and installed with their own package manager, and the script regenerates them when versions move. The script
  is `packages/fixtures/src/generate.ts`, and each project's own files are laid over the scaffold from
  `packages/fixtures/overlays`. `pnpm --filter @parity-app/fixtures generate [name]` regenerates a project, keeping its
  `expected.json`, and `pnpm --filter @parity-app/fixtures install-projects` installs every project in `fixtures/` from
  its lockfile, one at a time. Projects made some other way install with `npm ci` from their `package-lock.json`.
  Storybook's own init runs as it would in CI, so it leaves out its Vitest addon.
- **Never changed by a test.** Each run copies the project to a temporary folder first, so saves and installs don't
  touch the original. The copy links the project's installed packages rather than copying them.
- **Snapshots change on purpose.** When detection gets better, `pnpm vitest run packages/fixtures -u` rewrites the
  `expected.json` files, and the diff shows what changed. They're taken as of a fixed date, so the version cutoff
  doesn't change them by itself.
- **Run on every change, and on every system.** Detection and the render sweep run on each change. The editor flows run
  nightly and before releases, on Windows, macOS and Linux.
- **They set the statuses on this page.** ✅ means a validation project covers it and passes. ❔ means no project does
  yet.
